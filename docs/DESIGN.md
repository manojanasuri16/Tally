# Tally: design

Tally is a family payment book for Android, kept mostly for loans. Each phone keeps the whole book locally and works offline. Phones in the same family exchange changes through a relay that only ever holds ciphertext.

It is a sibling of Balance (`~/Balance/android`, package `com.balance.ledger`) and reuses its core helpers, ledger storage, crypto, file store, UI kit and translations approach. Balance itself is never changed by this project.

- Package and `applicationId`: `com.tally.book` (never change after the first release).
- Users: parents first. Large type, few choices per screen, Telugu and Hindi from day one.

## What it does

- Three kinds of loan:
  - `bank`: an instalment loan: principal, yearly rate, number of instalments, instalment (EMI), and how often it falls (every month, two weeks, week or day). Interest on what is still owed (reducing) or flat. A floating rate can change from a date.
  - `hand`: money borrowed from a person (or, with `direction: "given"`, money lent to one). Only interest is paid (monthly or yearly), or none at all; the principal stays owed until it is returned, all at once or in parts.
  - `gold`: a **loan against something** (`pledge`: gold, an LIC policy, a fixed deposit, land papers, or nothing, as for a crop loan or Kisan credit card). Interest only (yearly by default), principal repaid on closure, with an optional date to repay or renew by.
  - `card`: a **credit card**, kept from its statements: `principal` is the outstanding amount on the statement dated `startDate`, `minDue` the minimum due (0 = the whole bill) and `dueDate` the pay-by date. No interest is worked out; each new statement ("Update statement": `updateStatement`) replaces the three figures and the date, sets `statementAt`, and keeps the old ones in `statements` [ { date, outstanding, minDue, dueDate, by, at } ]. Payments (kind "principal", "Card payment") count against it when dated after the statement date, or on it if entered after the statement was (`at` > `statementAt`). What is owed is the outstanding amount less those; the one due item is the minimum (or the whole bill) less those, on `dueDate`, so Due this month, the totals, reminders and the widget take it like any other. Paying it to zero never offers to close the card. Kept simple: the form asks only name, bank, outstanding, minimum due and pay-by date (the statement date is the day it is entered, and Update statement uses today); a pay-by date already past just makes it overdue. **Credit limit** (optional): a card has its own `limit`, or shares another card's (`limitWith`: that card's id; e.g. two cards of one bank on one limit). Nothing is assumed from the bank: the form asks "Shares its credit limit with" (No, its own / the other open cards, never one already using this card's limit). Sharing follows `limitWith` to the card that shares with none (`limitRoot`; loops and missing cards end the chain), and that card's limit is the group's. The card screen shows Credit limit, Shared with and Available = the limit less what is owed on every open card on it, never below 0 (`cardLimitView`). **Billing days** (optional, days of the month): `billDay` (the statement is made) and `payDay` (it must be paid). With them a new card's statement date is the latest bill day (`lastBillDate`), Pay by fills itself with the first pay day after it (`payDateAfter`) until picked by hand, Update statement counts from the latest bill day and fills Pay by the same way, and the card screen asks "A new statement came on <date>. Update it." once a bill day has passed since the figures held (`newStatementSince`).
- Log a payment against a loan: amount, date, what it was for (EMI, interest, principal), and optionally a note, a pasted bank SMS, and photos or documents.
- Keep each loan's documents, added when the loan is made or later on its screen.
- Family sync: pull down to refresh. Every loan and payment shows who entered it. Admins let people in (one-time invites, approved by an admin), can remove members (the family's key is then replaced), and make others admins.
- A loan is shared by default. A private loan, its payments and its files never leave the phone, except inside a backup file the person makes.
- Backups: once a day into a folder on the phone (the newest 14 kept), Back up now through the share sheet, and Restore on a new phone.

## The local book

Same conventions as Balance (`android/PORTING.md` there): `DB` is an `Obj`/`Arr` JSON tree, every number a `Double`, unknown fields round-trip, every change goes through `Ledger.edit { }`, ids come from `uid(prefix)`.

```
DB = {
  v: 1,
  me:      { id, name },                       // this phone's person; id = uid("m")
  family:  { v: 2, id, name, creator, me: { secret, notice, pub, priv, at }, keys: { "<epoch>": key }, relayEpoch,
             role, roster, invites, pins, repins, usedInvites } | absent,   // sync/Membership.kt; absent until created or let in
  joining: { fam, name, inviter, invite, s, me, at, expires, back?, as? } | absent,  // a join request waiting for an admin
  familyGone: { name, why, at } | absent,       // "removed" | "replaced" | "denied" | "expired": told once on screen
  members: [ { id, name, pub, invite?, left?, at, updatedAt, updatedBy, deleted? } ],
  loans:   [ { id, kind, name, lender, principal, rate, startDate, note, private, closed, closedDate,
               interestMethod,                  // "reducing" (default: interest on what is still owed) | "flat" (on the original amount); bank loans only: interest-only entries are always on what is still owed, and an old one saved as "flat" is read as reducing
               paidUpTo,                        // optional ISO date, after startDate, not in the future: everything due on or before it was paid as agreed (a loan entered late)
               // bank only:
               tenure,                          // number of instalments (in the loan's frequency); 0 = work it out from emi
               emi,                             // the instalment; 0 = work it out from tenure (whole rupees)
               frequency,                       // "month" (default) | "fortnight" | "week" | "day"
               dueDay,                          // day of the month the instalment falls; monthly loans only (set from firstDue when given)
               firstDue,                        // optional ISO date after startDate: the first payment; every schedule counts from it (see below)
               rateChanges: [ { id, from, rate, emi? } ],   // floating rate: from that date the rate (and, with emi, the instalment) changes; reducing loans only
               // hand and gold:
               interestEvery,                   // "month" | "quarter" (3 months) | "half" (6 months) | "year" (hand: default month; gold: default year)
               rateUnit,                        // "year" (default: percent a year) | "month" (percent a month; "2 rupees interest" = 2)
               repayBy,                         // optional ISO date, after startDate: "to be returned by" (hand) / "repay or renew by" (gold)
               renewals: [ { id, date, from, to, by, at } ],  // renewLoan history: the repayBy moved from `from` to `to` on `date`
               direction,                       // hand only: absent/"taken" (money I took) | "given" (money I gave); never changed after the loan is made
               plan,                            // hand only: absent (interest only, or no interest when rate is 0) | "instalments" (fixed instalments, below)
               received,                        // hand with plan "instalments", optional: the money actually handed over (₹9,500 of ₹10,000)
               // a hand loan with plan "instalments" also has emi, tenure and frequency (as bank), and rate 0
               pledge,                          // gold only: "gold" (default) | "lic" | "fd" | "land" | "none"
               grams,                           // gold only, and only when pledge is "gold"
               by, at, updatedAt, updatedBy, deleted? } ],
  payments:[ { id, loanId, date, amount, kind,  // kind: "emi" | "interest" | "principal"
               note, sms, by, at, updatedAt, updatedBy, deleted? } ],
  files:   [ { id, ownerType, ownerId,          // ownerType: "loan" | "payment"
               name, mime, size, sha256, by, at, updatedAt, updatedBy, deleted? } ],
  sync:    { cursor, lastAt, dirty: { "<recordId>": true }, blobsUp: { "<fileId>": true },
             pushed: { "<recordId>": true } }        // ids the relay is known to hold (sync/SyncModel.kt)
}
```

- Money never nets out. For taken loans `totals()` gives `owed`, `dueThisMonth`, `paidThisMonth`, `byKind`, `pendingThisMonth`; for given loans `toReceive`, `expectedThisMonth`, `receivedThisMonth`, `pendingToReceive`. `dueList()` rows carry `given` and `kind` (`emi`/`interest`/`principal`). On screen a given loan reads "Still to come back", "Log money received", "Expected this month", "Received".
- The loan rules are below ("Loan rules"); the code is `model/LoanMath.kt` (arithmetic), `model/Loans.kt` (view, due list, totals, checks), `model/LoanLabels.kt` (labels and wording), `model/Reminders.kt`, and the writes in `model/Records.kt`.
- `by` / `updatedBy` are member ids; `at` / `updatedAt` are epoch milliseconds from `Clock.millis()`.
- Dates are ISO `YYYY-MM-DD`, device-local.
- Deleting sets `deleted: true` (a tombstone) so the delete can travel. Tombstones are hidden everywhere in the UI.
- Every write helper in the model stamps `updatedAt`/`updatedBy` and marks the id in `sync.dirty`. Screens never do this by hand.
- A payment or file is private exactly when its loan is private (`isPrivate(record)` resolves through the owner).

## Loan rules

All figures come from the payments actually logged; nothing is added to what is owed. Amounts are rupees (`Double`); an EMI and a period's interest are whole rupees, everything else is kept exact and rounded only on screen.

**What is owed** is the principal still outstanding. Interest or instalments that fell due and were not paid are **pending**: shown beside it, never added to it.

### Instalment loans (`bank`)

- **First payment date** (`firstDue`, every kind with a schedule): payments are often due on another day than the one the money came. When set and after the start date, the k-th due is: monthly, the firstDue's day in the (k−1)-th month after it; every 14, 7 or 1 days, firstDue + (k−1) steps (so the weekday is firstDue's); interest-only, every 1, 3, 6 or 12 months from it on its day. Each interest-only period still charges one full period's interest. Without it (or with one on or before the start) the rules below apply. The form always shows it, pre-filled with the usual date (`defaultFirstDue`), and stores it only when the user picks a date.
- **Instalments** fall every month (on `dueDay`, clamped to the month's last day; the first is the first due day after the start date), or every 14, 7 or 1 days from the start date (so a weekly or fortnightly loan keeps the start date's weekday; `dueDay` is ignored). `tenure` is the number of instalments. The periodic rate is the yearly rate / 12, 26, 52 or 365.
- **Reducing** (default): EMI = P·r·(1+r)^n / ((1+r)^n − 1), to the whole rupee. Each instalment's interest is what is owed × r at the rate in force on its due date; the rest of it is principal.
- **Flat**: total interest = P × yearly rate × (n / instalments a year); instalment = (P + total interest) / n, to the whole rupee. Every instalment carries the same interest part, P × yearly rate / instalments a year; the rest is principal.
- With only an EMI given, the number of instalments is worked out from it; with only a count, the EMI. The **last agreed instalment** takes the few rupees left over from rounding the EMI (when what is left differs from the EMI by at most n + 1 rupees), so a 12-instalment loan has exactly 12.
- **EMI payments cover instalments in order, oldest first.** A partial payment covers part of one (what is left on it is the next amount due); a double payment covers two. An instalment's interest is charged once, however many payments it takes. `principal` payments (part-payments) lower what is owed at once. `interest` payments on a bank loan are only counted as interest paid.
- **Part-payments:** reducing: the instalment stays, fewer are needed. Flat: the instalment and its interest part stay the same, fewer are needed, and the instalments no longer needed (with their interest) are simply not charged: instalments left = what is owed / principal part, rounded up, and the last is what is left plus its interest.
- **Rate changes** (`rateChanges`, reducing loans only): every instalment due on or after `from` uses the new rate for its interest; with `emi` it also uses the new instalment. Without `emi` the instalment stays and the number left follows. Instalments due before `from` are never recomputed. Two changes on one date are not allowed (`addRateChange` replaces one on the same date).
- **Pending:** instalments whose date is before today and that are not fully covered (`emisPending`, `amountPending`). The instalments left, the end date, and the amounts of the ones not paid yet are worked forward from what is owed now. An EMI too small to ever clear the loan sets `emiTooLow` (and validation refuses one at or below the first instalment's interest).

### A person's instalment loan (`hand` with `plan: "instalments"`)

- A lender who hands over ₹9,500 for ₹10,000 and collects ₹1,000 every week for 12 weeks. The form asks the amount, what was actually received (optional), how often, each payment and how many.
- It is worked exactly as a bank loan with no rate whose amount is the instalments' total (`instalmentBasis`): what is owed is what is left of `emi × tenure` (₹12,000), EMI payments cover instalments in order, pending and the due list work as for a bank loan, and a monthly one falls on the start date's day. `loanView` adds `totalToRepay` and `extra` (the total less `received`, or less the amount when `received` is not given). It has no repay-by date and no rate changes.
- Payments on it are "Instalment" (`emi`) and "Returned some of the amount" (`principal`, lowers what is owed at once).

### Interest-only loans (`hand` with a rate, `gold`)

- **Periods** end every 1, 3, 6 or 12 months after the start date, on the start date's day (clamped), or from `firstDue` when given.
- A period's interest is worked on what was owed at its start (part repayments dated on or before that day count), so a part repayment lowers the interest from the next period. There is no flat interest here: an old entry saved as "flat" is read the same way.
- **Interest payments cover periods in order, oldest first;** a partial payment covers part of one. **Pending** (`interestPending`, `periodsPending`): the uncovered part of every period that ended before today, since the start or since the last period fully paid. Interest is counted only for whole periods that ended while something was still owed: when the whole amount is returned mid-period, that last part-period is not worked out (settle it by hand as an interest payment).
- A loan with `rate: 0` (hand or gold) has no interest: no next due, never pending, never overdue, simply still owed. Its only payment kind is a part repayment, which lowers what is owed.
- The form asks a person's entry "How is it paid back?": **Interest only** (the default), **No interest**, or **Instalments** (above). With a rate it shows the interest a period works out to ("Interest: ₹1,000 every month (₹2 on every ₹100 a month)").
- **Repay by** (`repayBy`, hand and gold): from the month it falls in, the remaining amount is a principal row in the due list, overdue once the date has passed while anything is owed. **Renewing** (`renewLoan`) moves the date and keeps a `renewals` entry; it does not touch interest: whatever interest is pending stays pending until it is paid as an interest payment.

### A loan entered after it started (`paidUpTo`)

- Every instalment (bank) or interest period (hand, gold) dated on or before `paidUpTo` counts as paid as agreed, with no payments logged for it; `loanView` gives `paidUpTo` and `paidUpToCount` (how many it covered). `suggestPaidUpTo(draft, today)` gives the form the most recent due date before today by the draft's schedule (for a bank loan at most its agreed number of instalments), "" when none.
- Bank loans: what is owed follows the schedule to that date: reducing, each covered instalment pays its interest at the rate in force on its date (rate changes before `paidUpTo` included) and the rest is principal; flat, P minus the covered principal parts.
- Hand and gold loans: the principal is not changed by `paidUpTo`. **If part of the amount was already returned before that date, enter what was still owed on that date as the amount**, since interest after it is worked on that.
- Logged payments dated after `paidUpTo` work as always. Payments dated on or before it are counted in `paidTotal` (and in the month's paid totals) but cover nothing and lower nothing: the date already accounts for them. Nothing is invented: `paidInterest`, `paidPrincipal` and `paidThisMonth` come from logged payments only.

### Due list, totals, suggestion, reminders

- A loan's instalment/interest row in `dueList()` is everything unpaid dated up to the end of this month (every weekly or daily instalment of the month), dated by the oldest one, split into `pending` (before today) and `upcoming`, with `count`. `totals().dueThisMonth` is the sum of the rows for money I took (so it includes what is pending; `pendingThisMonth` is that part).
- `suggestPayment()`: a bank loan, what is still to pay on the oldest unpaid instalment; hand and gold, one period's interest on what is owed now (pending interest is shown separately and the person decides); a no-interest loan, a part repayment of 0.
- `remindersFor(today, horizonDays 0..3)`: for every open loan on this phone, one overdue item (everything pending), one item for today, one per day within the horizon, and the repay-by date as a principal item; counted separately for money I took and money I gave (expected back). A reminder notification built on it names no loan, person or amount.

## Sync

Sync version 2 (Tally 0.3.0). Families made by 0.1.0/0.2.0 (one shared key inside the invite, one family token) are not carried over: see "Old families".

### Keys and epochs

- **The family keyring:** `(epoch, key)` pairs, each key 32 random bytes, epoch 1 made by the phone that creates the family. A new epoch is made by an admin's phone whenever someone is removed or leaves (see "Membership"). Phones keep every epoch they were given, so everything written before stays readable to current members; nothing is ever re-encrypted.
- **Why old records are not re-encrypted:** everything sealed under an old key was readable by whoever held that key, and a removed member keeps their copies anyway; re-sealing would cost every phone a full re-upload (and the free tier the bytes) and take nothing away from anyone. What matters is that nothing *new* is written under a key a removed member held, and the relay refuses exactly that (`p_epoch` must be the family's newest).
- `encKey(epoch)` = HKDF-SHA256(key of that epoch, no salt, info `"tally-enc"`, 32 bytes): AES-256-GCM for every record, file and invite box.
- Record AAD: `"tally:<familyId>:<recordId>"`. File AAD: `"tally-file:<familyId>:<fileId>"`. A blob cannot be replayed under another id or family.
- A sealed blob (version 2) is base64 (standard, padded) of `2 || epoch (4 bytes, big-endian) || iv (12) || ciphertext || GCM tag (16)`; the 5-byte header is fed to GCM ahead of the AAD, so neither the version nor the epoch can be changed undetected. Version 1 blobs (`1 || iv || ct`, one key, no epoch) are still readable by `SyncCrypto.open`, but nothing writes them and the v2 relay holds none.
- **Member identity:** for each family it joins, a phone makes an EC P-256 key pair (JDK/Android `KeyPairGenerator` + `KeyAgreement` ECDH; no new dependency) and two random 32-byte credentials: the **relay secret** (hex; the relay stores only its SHA-256) and the **notice token** (hex; can only ask "any join requests?"). All three live in `DB.family.me`.
- **Sealing to a member** (key boxes): ECIES. An ephemeral P-256 key pair, ECDH with the recipient's public key, HKDF-SHA256(Z, salt = ephemeral SPKI ‖ recipient SPKI, info `"tally-box-v1|" + context`), AES-256-GCM with the context as AAD. Blob: base64(`1 || ephemeral SPKI (91 bytes) || iv || ct`). Context: `"tally-box:<familyId>:<memberId>:<epoch>"`, so a box opens only for that member and epoch.
- **Where the private key lives, and why:** in the book (`DB.family.me.priv`, PKCS#8), next to the keyring. Android Keystore can do ECDH only from API 31 (minSdk is 29), and a Keystore key cannot go into a backup, while a restored phone must stay the same member (it needs the private key to open keys sealed to it after the backup was taken, and the secret to talk to the relay). The book is sealed with the app lock when one is set, so the private key is exactly as protected as the family keys it guards; without a lock both are plain on the phone (as the family key always was). A backup therefore holds the member's credentials and keyring (see "Backups").

### Invite

`tally://join#t2.<familyId>.<secret>.<expires>.<base64url(familyName)>[.<base64url(inviterName)>]` (base64url without padding), shown as a QR code and shareable as text. **It never carries a family key.**

- **Fresh each time:** every "Invite someone" makes a new invite: 32 random bytes `secret`, used once, valid 24 hours, cancellable. Any member can make one; only admins let anyone in.
- `expires`: epoch seconds, decimal; the phone that scans refuses an expired code before asking anything. The relay keeps its own 24 hours.
- From the secret: `inviteId` = base64url(HKDF(secret, `"tally-invite-id"`, 16 bytes)) (the only name the relay knows the invite by), `requestKey` = HKDF(secret, `"tally-join-req"`), `grantKey` = HKDF(secret, `"tally-grant"`). The secret itself never reaches the relay: the inviting phone registers the invite as `inviteId` plus an **invite box** (`{ s, by, exp }` sealed under the family's newest key, AAD `"tally-invite:<familyId>:<inviteId>"`), so the family's admins (members) can recover the secret and nobody else can.
- The family id is 16 random bytes, base64url (22 characters). Names: 1 to 80 characters, no control characters (a longer inviter name is shortened, a blank one left out). `Invite.parse` is strict (exactly the tag `t2`, canonical base64url, a 32-byte secret, a canonical decimal expiry, valid UTF-8 names); the whole text is at most 1024 characters. `Invite.find` picks the link out of a whole shared message.
- **Old invites** (`tally://join#<familyId>.<key>.<name>[.<inviter>]`, three or four parts, from 0.1.0/0.2.0) are recognised by `Invite.isOld` and refused with "This code is from an older Tally. Ask for a new one."
- One family name, typed by whoever starts the family; everyone who joins stores that same name, never the inviter's. An admin can rename it later ("The family's name" below).

### Joining (approval)

1. **Scan.** The joining phone parses the code, refuses it if expired, and asks "Join <family>?", "The invite link says it is from <inviter>. Tally can't check the names in a link. Join only if you know who sent it." (both names come from the link, which anyone can make with any names, and a `tally://join` link can open the app from any web page or chat).
2. **Request.** It makes its identity (key pair, relay secret, notice token) and sends `tally_join_request(familyId, inviteId, memberId, sha256(secret), sha256(notice), blob)`, where `blob` = AES-GCM under `requestKey` of `{ name, pub }` with AAD `"tally-join:<familyId>:<inviteId>:<memberId>"`. The relay marks the invite used (one request per invite) and keeps the request for 72 hours. The phone keeps `DB.joining` (the family's name, the inviter, the invite id and secret, its new identity); nothing of the family is in the book yet.
3. **Notice.** Admins' phones see the request on their next sync (and the background check, "Notices", says that someone asked).
4. **Check (admin's phone).** From `tally_state` it gets the request with the invite's box. It refuses (and turns down at once, so nothing is shared) a request when: the invite box is not sealed under the family's current epoch, does not open, names another maker than the relay says, or its secret does not derive this invite id; the request blob does not open under that invite's `requestKey` for exactly this member id (so a swapped public key or member id fails); the member is already active; this phone has already decided that invite, or any member's record names it (a replay); two requests come for one invite. Otherwise it shows "<name> wants to join <family>. <inviter> invited them. Allow?" (the name from the sealed request, the inviter from the invite box).
5. **Allow.** The admin's phone seals a **grant** to the joiner's public key: every key the family has (epochs 1..now), the admin's pinned member keys, the creator's id, and a MAC under `grantKey` over all of it (bound to family, member, public key and invite id). `tally_request_decide(allow, epoch, box)` makes the joiner an active member with the credentials it sent, stores the grant as its box for the current epoch, and deletes the request and the invite. The admin's phone also writes the new member's record (name, public key, invite id) so every phone pins the key the admin checked. **Don't allow**: `tally_request_decide(allow = false)` keeps the request as `denied` until it expires; nothing is shared.
6. **In.** The joining phone polls `tally_join_status` on each sync (`pending` / `denied` / `approved` / `removed`, or gone). On `approved` it fetches its boxes, opens the grant with its private key and checks the MAC with the invite's `grantKey`; a grant that does not check out (a relay that sealed keys of its own to the joiner's public key) is refused and the phone keeps waiting. Then it enters the family and syncs. **Nothing already on the phone is shared yet** (`SyncModel.holdExisting`: every record in the book is held in `sync.held`; `collectPush` and `planBlobs` skip held entries and anything whose loan is held, even when edited meanwhile). When the book had shared entries, the Family page and the home screen show one card: "Share your existing entries with <family>?", how many, and who is in the family (from the first pull), with **Share all** (`answerShare(true)`: they go up with the next sync) and **Keep them on this phone only** (`answerShare(false)`, asks once: every held loan becomes private, so it and its payments and files never leave the phone; the person can share one later by turning off Keep private). Entries made after joining are shared as usual. The joiner's own member record is the one the approving admin wrote (with the admin's certificate for its key, see "Who wrote what"), taken from the first pull. On `denied` or a request that expired it forgets the request and says so once (`DB.familyGone`).

### The family's name

An admin can rename the family (`SyncEngine.renameFamily(name)`; the same name rules as creating one). The name is a small **meta** blob on the relay, `tally_family.meta`: `{ name, v, at, by }` sealed by the admin's phone with `SyncCrypto.sealE` under the family's newest key, AAD `"tally-meta:<familyId>"`, so the relay never sees the name. It is stored only through `tally_family_meta_set`, which takes the family lock and refuses anyone who is not an admin (`TA006`) and any epoch but the newest (`TA002`, retried after a refresh). A record-level value was not used because any member can push records and the relay cannot read their kind, so "admins only" could not be enforced there.

`tally_state` hands the blob to every active member; each phone opens it with its keyring and takes the name when `v` (one more than the version the renaming phone had seen) is not older than its own `DB.family.nameV`, so an older name replayed by the relay is ignored and an unreadable blob changes nothing. A phone let in after a rename has every key in its grant, so the first state it reads gives it the new name, whatever its invite said; invites made after a rename carry the new name (`newInvite` uses `DB.family.name`). A rename after a removal is sealed under the new key, which the removed member never had. Covered by `SyncRenameTest` and the live check.

### Membership: admins, removing, leaving

The rules (enforced by the relay, `supabase/migrations/*_tally_membership.sql`, and mirrored by `FakeRelay` in the tests):

- Whoever creates the family is its **creator** and first **admin**.
- An admin can make any active member an admin, and take the role from any admin, except: never from the last admin, and never from the creator (only the creator can step down). (The owner's rule "nobody can remove the creator" is extended to the creator's admin role, so the creator cannot be quietly sidelined either.)
- An admin can remove any active member, another admin included, except the creator and themselves (they leave instead). Nobody can remove the creator; the creator can leave.
- Any member can leave on their own. If the last admin leaves, the longest-standing remaining member (earliest joined, then id) becomes admin. When the creator leaves the family has no creator any more (nobody is protected). When the last member leaves, the family and everything it holds on the relay is deleted.
- Any member can make an invite and cancel their own; an admin can cancel any. Only admins see and decide join requests.

**Removing** (`tally_member_remove`), in one relay transaction: the member's status becomes `removed`, so every call with their credentials fails from that commit on (`TA001`); the family moves to epoch `n+1`; the admin's phone has made the new key and sealed a **rotation box** to each remaining active member whose public key it has pinned (its own included): `{ keys from has+1 .. n+1, MAC under HKDF(key of epoch has, "tally-box-auth") }`, where `has` is the newest epoch that member was given. A box for the removed member, or for anyone not active, is refused. Every open invite and request is deleted. On the removed phone the next sync (any call) hears `removed`: it forgets the family (like leaving), keeps every record, and says once "You were removed from the family. Your entries stay on this phone." **What the removed person already has stays on their phone: the records, files and old keys they synced before. Nothing can claw that back.** What they can no longer do is read anything new (the relay will not serve them, and new data is under a key they never had) or write anything.

**Leaving** (`tally_leave`): the status becomes `left`, their invites go, the successor rule above applies, and the family is marked `rotate`: the next sync of an admin's phone makes a new epoch the same way (`tally_rotate`). Without internet the phone leaves locally at once and tells the relay on a later sync (`DB.leaving`).

**A phone that missed a rotation** finds its boxes in `tally_state` on the next sync and opens them in order (each proved by a key it already holds). A member the rotating phone could not seal to (no pinned key yet, or let in while the rotation was being made) has `has` < the family's epoch; the next sync of any admin's phone that has its pinned key gives it a box (`tally_box_put`). Until then that phone reads but pushes nothing (`SyncResult.Done(waitingForKey = true)`).

**Pins:** a member's public key is pinned the first time a phone learns it, only from something an admin vouched for: its own; the admin's check at approval; a grant's pins; or an admin's **certificate** in the member's record (see "Who wrote what"). A member record's `pub` alone pins nothing (any member can write a member record), and a pinned key is never replaced by a later record. Only two things replace one: an admin approving that member id again, and a **re-pin** (a member back on a new phone, below) carried inside a key box that checked out. Rotation boxes are sealed only to pinned keys, never to anything the relay says.

### Back on a new phone

A member who lost or replaced their phone comes back **as the same person** (same member id, so everything they added keeps their name; their admin role and joined date stay), approved by an admin. Code: `SyncEngine.requestJoin(invite, back = true)`, `approveAs`, `joinStep`; relay: `supabase/migrations/*_tally_rejoin.sql`.

1. **Ask.** On the new phone the person opens a fresh invite (scan, paste or link) as anyone does, ticks "I was already in this family (new phone)" and joins with their name. The request is the ordinary sealed one with `back: true` inside the seal (an ordinary request is byte-for-byte as before), so the relay never knows. It is made under the phone's own id, or a fresh one when that id is already a member (a restored book). The joiner never learns the member list before it is let in.
2. **Pick.** An admin's phone checks the request exactly as any other (`Membership.check`) and shows "<name> says they are back on a new phone. <inviter> invited them." with the new phone's **code** ("Their new phone shows a code. Call them and ask them to read it: it must be 1234 5678": `Membership.phoneCode`, 8 digits of SHA-256 of the new phone's public key, also shown on the waiting phone), a member picker ("This is …", **nobody picked** until the admin chooses: the name in a request proves nothing), **Allow as <member>** (asks once, naming the member, the code to compare, and for an admin "this phone will be able to let people in and remove them"), **Allow as someone new** (the ordinary approval), **Don't allow**. Only a request that said `back` can be allowed as an existing member (`Refused` otherwise). **Who can be handed over** (the relay enforces it, `tally_member_reclaim` in the tally_hardening migration; the card shows why instead of the button, `MemberText.allowAsBlocked`): the creator's place only by the creator's own old phone (the creator approves their new phone themselves); another admin's place only when the approving admin did not make the invite the request came with, so a second person takes part (someone else makes the invite, or another admin approves); a member's place by any admin, as before.
3. **Allow as <member>** (`approveAs` → `tally_member_reclaim`, one transaction under the family lock, admins only, the target must be an active member): the member's credentials become the ones the new phone sent; the old credential's hash goes into `tally_replaced`; the member's old boxes are deleted; and the family moves to epoch `n+1` (`tally_new_epoch`, as a removal: every open invite and request goes). The boxes: the **grant** for the member, sealed to the new phone's public key and MAC'd with the invite's grant key over keys `1..n+1`, the admin's pins and the creator, **sealed for that member id** (box context and MAC); and a rotation box for every other active member with a pinned key, each carrying the re-pin `{ member: new key }` (a box's `pins` are covered by its MAC). The admin's phone re-pins the member, remembers it in `family.repins` (every box it seals from then on carries its re-pins, so a member that missed the rotation still learns the new key from a later repair box), and writes the member's record with the new `pub`.
4. **In.** The new phone asks `tally_join_check`, which answers `approved` and the member id it now is. That id is only the relay's word: the phone fetches its boxes as that member and takes only a grant that opens for exactly that id and checks out with its invite's grant key; anything else (a relay naming another member, or replaying another phone's grant) is refused and the phone keeps waiting (`Unverified`). Then it takes that id as `DB.me.id` (records it wrote before it was in any family are rewritten to it, `SyncModel.rewriteAuthor`) and enters the family; its own member record is pulled (the admin wrote it) rather than pushed over, and kept carrying its key.
5. **The old phone**, on its next call with the old credentials, gets `TA007` (`SyncError.Replaced`): it forgets the family like a removal, keeps every record, and says once "This phone was replaced by a new phone. It is no longer in <family>. Your entries are still on this phone." Nothing new is readable with its keys (new epoch).

**Phone upgrade:** the old phone may still be in use; the admin may even be the person moving (an admin approves their own new phone on the old one, which then retires). **Allow as someone new** leaves the old phone as it was.

**Private entries and old files** are not on the relay; they come back only from a backup. **Recommended order: restore first, then come back** (the Join screen says "Have a backup from your old phone? Restore it first from the welcome screen."):
- *Restore first:* the restored phone is the old member at once (same credentials), so it syncs. To retire the old phone (lost or stolen), it then asks to come back with a fresh invite and the box ticked: allowed while it holds that same family, it keeps syncing as before while it waits, and on approval only its credentials, keys and pins change (`Membership.reseat`); records, private loans and sync state stay. If the member had already been replaced or removed, the first sync says so and forgets the family (records kept), and the person comes back as above.
- *Come back first, then restore:* restoring the old phone's backup would bring back replaced credentials. So a restore keeps this phone's newer place in the family when both books are the same member of the same family and this phone's credentials are newer (`Membership.keepNewerSeat`, by `family.me.at`): the backup's loans, payments and private entries come in, with this phone's credentials and every key of both.
- Shared files: the member keeps owing files under the same member id, so the returning phone downloads whatever the relay still holds for that member; files the relay no longer holds come from the backup, or by "Ask for this file" from a phone that has them (see "Files").

**The only admin.** Nobody but an admin can let a member back in, and a non-admin can never approve, not even when "no admin is active" (the relay cannot tell a lost phone from a quiet one, so that rule would let any member take over the creator). The safe rule chosen instead: when the only admin first has someone else in the family, their phone says once "Make someone else an admin too, in case you lose this phone." (`MemberText.needsSecondAdmin`, `DevicePrefs` `tally-admin-hint`). An only admin who loses their phone without a backup cannot be let back in, since nobody can approve (the others keep sharing as before, but nobody can be let in any more); with a backup, restoring it makes them the admin again, and they can then retire the old phone by coming back as themselves and approving it on the restored phone. The creator is re-claimed only by an admin's approval like anyone else, and stays the creator (same id).

**Concurrency:** every relay function that changes a family takes that family's advisory lock before checking the caller, so two admins acting at once are put in one order and see each other's result. Approvals, rotations, removals and pushes carry the epoch they were made for; a stale one fails with `TA002` and the phone refreshes and retries (up to three times). Two admins approving one request: the second gets "gone". One removing while another rotates: the second's epoch is stale; a rotation that lost to another one is simply dropped (the other one already rotated).

### Threat model

The relay is trusted for availability only, never for confidentiality or for who is who.

- **A hostile relay (or anyone who reads its database)** sees: family ids, member ids, roles, statuses, epochs, invite ids, record ids and kinds, sizes, timing, hashes of credentials, and ciphertext. It **cannot**: read any record, file, name, request or key (all sealed under keys it never has); forge a record (AES-GCM, AAD bound to family and id); swap a joiner's public key or member id in a request (the request is sealed under a key derived from the invite's secret, which it never sees); impersonate an admin to a joiner (the grant's MAC needs the invite's secret); hand a member a key of its own (a rotation box's MAC needs the member's previous key, a grant's the invite's secret); make an admin seal a new key to it (rotation boxes go only to pinned keys); get a replayed invite through (one request per invite; the admin's phone refuses invites it has decided and any second request). It **can**: refuse service, drop or delay anything, hide a rotation or a request, show stale state, and learn the metadata above. A phone that is shown a newer epoch it cannot verify simply waits (nothing is written under a key it cannot check).
- **A removed member** (with an honest relay): rejected at once for every call; cannot read anything written after the removal (new epoch), cannot write. Keeps what was already on their phone.
- **A removed member colluding with the relay operator** (out of scope, stated plainly): the relay could hide the rotation from a phone, which would then keep writing under the old key the removed member holds; or hide the removal record from another admin, which might later seal keys to them. Detecting a hiding relay would need signed membership history; not in this version.
- **A leaked QR / invite text** (someone photographs the code): they can send one join request, within 24 hours, before the real joiner does. An admin must still allow it, and sees the name they typed and who made the invite; the real joiner's request then fails ("does not work, ask for a new one"), which is the signal. Cancelling the invite stops it. A leaked code never gives anyone the family's data by itself.
- **A stolen unlocked phone or a plain backup** holds the member's credentials and keys: it is that member. An admin removing that member ends it for everything new; or the person comes back on a new phone (an admin allows it), which retires the stolen phone's credentials (`TA007`) and moves the family to a new key in the same call.
- **Taking over a member** ("back on a new phone") needs an admin's approval on the relay (`tally_member_reclaim`, admins only, an open request from a fresh invite, an active target); nobody takes a place by themselves, and a non-admin never approves. The relay cannot move the place to another member (the grant is sealed and MAC'd for the member the admin picked, and the joining phone takes only that) nor replay a grant (bound to the invite's secret and the new phone's key). A thief holding a member's unlocked phone could make an invite and ask to "come back" as that member: the admin sees "<name> says they are back on a new phone. <inviter> invited them.", picks the member themselves (nothing is pre-selected) and is asked to call the person and compare the new phone's code. Nobody but the creator's own phone can hand over the creator's place, and an admin's place needs a second person (the review's M1).
- **Re-pins** ride in key boxes, so a removed member colluding with the relay, holding an old key a phone still builds on, could forge one; this is the same out-of-scope collusion as hiding a rotation.
- **A current member** can read everything they are given and add or edit entries (trust within the family is the point), but since the review of 2026-11-12 cannot: delete or hide someone else's entry (a tombstone is taken only from its maker, its loan's maker or an admin; a shared record saying `private: true` is never taken); rename another member, mark them gone, or put a key of their own in their record (a member record is taken only from that member or an admin); get another phone to pin a key for someone (pins come only from an admin's certificate); or make a record win for ever with a future date (clamped to 10 minutes ahead). Who *first* made an entry (`by`) on a record the phone sees for the first time is still only the writer's word; who *last* changed it is proved by the signature when it matters (deleting). Edits of someone else's entry are allowed and are not undoable from the app.
- **A hostile relay and old copies:** a phone takes a pulled row only when it is the same version or newer than its own (updatedAt, then updatedBy), so a relay replaying an older ciphertext cannot roll a phone back, nor undo a deletion (the phone sends its newer copy back up). It still can: withhold updates (a phone simply does not see them), serve an old copy to a phone that never had the newer one (a new phone joining, or one that was away), and drop anything.
- **Anyone with the APK** (the URL and publishable key are in it): cannot fill or freeze the relay any more (see "Limits"): starting families costs a proof of work and is limited per source address (Cloudflare's `cf-connecting-ip`; a forged `CF-Connecting-IP` is refused by Cloudflare and a forged `X-Forwarded-For` is ignored, checked live on 2026-11-12) and relay-wide; each family has a byte budget; the relay refuses growth at its own ceiling, below the size at which Supabase would make it read-only; a family's downloads are capped per day. Someone with many addresses can still start families up to the relay-wide window (100 an hour, 500 a day) and fill the relay up to its ceiling: new growth then stops for everyone (existing families keep reading, deleting, removing and rotating) until the owner deletes the abusive families; the alert (50 %, or 25 MB of growth in a day) gives time for that.
- **Files in transit** (see "Files"): the relay learns which member is owed which file id, when each is collected, and who asked for which file id: the same kind of metadata as above (file ids were already visible as record ids of kind `file`). It still never sees a file's bytes, name or type. A hostile relay can drop a file early, or keep it past 30 days (it is sealed either way), or claim a member is owed a file: the phone fetches only bytes that open under the family key and match the record's SHA-256, and acknowledges nothing else. An ask is member-authenticated, carries only the file id, and is answered only from bytes a holder has checked against the record, never for a private loan's file. The usage call (`tally_relay_usage`, no credentials) gives only relay-wide totals.

### The relay (Supabase)

`supabase/migrations/20261112013706_tally_membership.sql` (and `20261112020514_tally_not_admin_code.sql`, `20261112060000_tally_family_meta.sql`, `20261112105803_tally_rejoin.sql`, `20261112111559_tally_files_in_transit.sql`). Row level security is on for every table with no policies and no grants to `anon`/`authenticated`, so the Data API reaches nothing directly. All access is through `security definer` functions in `public` with `search_path = ''`; helpers live in the unexposed `tally_private` schema.

Since the tally_hardening migration the default privileges of everything postgres creates give `anon`, `authenticated` and PUBLIC nothing, so a later table, sequence or function is reachable only through an explicit grant; `SyncHardeningTest.everyNewRelayObjectRevokesTheDefaultGrants` also checks that every migration revokes what it creates. Private bookkeeping in `tally_private`: `tally_secret` (the pepper for address hashes), `tally_create_log` (when, source hash, which header), `tally_usage` and `tally_usage_log` (the database size, hourly for eight days).

Tables: `tally_family` (id, creator, epoch, rotate, record_count, blob_bytes, meta, record_bytes, box_bytes, last_active, egress_day, egress_bytes), `tally_member` (family, id, secret_hash, notice_hash, role, status, has_epoch, joined_at), `tally_replaced` (family, member, secret_hash, replaced_at: credentials a new phone replaced), `tally_invite`, `tally_request`, `tally_box`, `tally_record`, `tally_blob` (family, id, data, uploader, created_at, expires_at), `tally_blob_owed` (family, file id, member: who still needs a file), `tally_file_ask` (family, file id, member, created_at: "Ask for this file"). A trigger on `tally_member` drops what a member is owed and has asked for when its status stops being `active`. The version-1 tables (`tally_families`, `tally_records`, `tally_blobs`, sequence `tally_seq`) are left in place with their rows, unreachable; a later migration can drop them.

### Limits

Chosen for a family app on Supabase's free tier (500 MB database, 5 GB egress a month), so that a stranger with the APK cannot fill or freeze it (`supabase/migrations/*_tally_hardening.sql`, mirrored by `FakeRelay`, tested by `SyncHardeningTest`). Files pass through only in transit, so the file cap is what a family can have **waiting** at once, not what it keeps; at the cap a phone keeps the rest queued and sends them on a later sync, once others have collected theirs. A GitHub check every three hours (`.github/workflows/keep-awake.yml`, after the ping) reads `tally_relay_usage` and fails the run, so GitHub emails the owner, when the whole database is above 50 % of 500 MB or grew by more than 25 MB in 24 hours.

| Limit | Value |
|---|---|
| active members per family | 20 |
| live (unused, unexpired) invites per family | 5 |
| open join requests per family | 5 |
| records per family | 20 000 |
| bytes of records and key boxes per family | 5 MiB while it has only ever had one member, 20 MiB after |
| the whole relay | no growth (pushes that add bytes, files, new families) once the families hold 300 MiB or the database is above 425 MiB; removals, rotations, approvals and deletions always work |
| downloads per family | 200 MiB a day (pulls and files together) |
| key epochs per family | 300; each member keeps its newest 20 boxes, and boxes of members no longer active are deleted |
| a family of one nobody pulls for 60 days | deleted by `tally_ping` |
| files in transit per family | 50 MiB at a time (a file at most 6 MiB sealed; a stored file at most 4 MB); each kept at most 30 days |
| open "Ask for this file" requests per family | 500 (each kept 30 days) |
| new families | a 20-bit proof of work each; 5 an hour and 20 a day per source address (IPv6 by /64; kept only as a peppered hash, two days); 100 an hour and 500 a day across the relay |
| invite lifetime / request lifetime | 24 hours / 72 hours |
| rows per push / per pull | 500 / 500 (and at most 4 MiB per pull page) |
| a relay answer the phone reads | 10 MiB (`HttpRelay.MAX_RESPONSE`; anything bigger is refused) |
| record blob | 64 KiB |

A join request needs a live invite id (derived from a secret only the QR has), so strangers cannot send requests at all. Expired invites and requests are deleted by the next invite or request in that family and by the daily `tally_ping`. A family whose last member leaves is deleted with everything in it.

### One refresh

0. A leave the relay has not heard of is sent. A waiting join request is checked (`tally_join_status`); once allowed, the grant is checked and the family entered.
1. `tally_state`: new key boxes are opened (each proved with a key already held) and the keyring grows; the roster, my role and the creator are cached in `DB.family` for the screens, and a newer family name is taken. Removed → forget the family, keep the records, say so once.
2. **Pull** everything with `seq > sync.cursor`, page by page until a page comes back empty (a page holds at most 500 rows and 4 MiB, so a short page is not the end); each row is opened with the key of the epoch in its header, its signature checked, and merged by the "Merge rules" below. Member keys vouched for by an admin's certificate are pinned. The cursor moves in the same save as the page it covers.
3. **An admin's phone:** rotates if the family is marked `rotate`, gives boxes to members lacking the newest key, and checks open join requests (`SyncEngine.requests`); requests that do not check out are turned down.
4. **Push** every dirty record that is not private and not held (see "Joining", step 6), signed (see "Who wrote what") and sealed under the newest epoch, with that epoch (a phone that lacks the newest key pushes nothing).
5. **Files** (see "Files"): `tally_files` says which files this member is owed and which ones others asked for. Upload the bytes of each id in `sync.blobsUp`, and again those of any asked-for file this phone holds (same epoch rule); download every file this member is owed, and acknowledge each (`tally_blob_ack`) only once it is stored here and read back matching the record's SHA-256.

On the wire a record is the sealed envelope `{ "k": "loan"|"payment"|"file"|"member", "r": { ...the record... } }`, as in version 1, and the merge, privacy and restore rules below are unchanged. A member record now also carries `pub` (that member's public key in this family), `invite` (the invite it came in with) and, once removed or gone, `left: true`.

### Merge rules

`SyncModel.mergeRemote(db, rows, trust, now)`, pure and covered by `SyncModelTest` and `SyncHardeningTest`. In order, for each pulled row:

1. An `updatedAt` more than 10 minutes (`SKEW_MS`) ahead of this phone's clock is pulled back to now + 10 minutes (and its signature dropped).
2. A loan, payment or file that says `private: true` is never taken (an honest phone sends a private record only as a bare tombstone).
3. A member record is taken only when its proved writer is that member or an admin; before that, a certificate in it may pin the member's key. Refused, and this phone holds a proved copy, the copy is marked dirty so it goes back up (someone wrote over it on the relay).
4. Not in the book: added. A different kind under the same id: ignored. Private here: as before (ignored and re-marked; taken after a restore when newer).
5. A tombstone over a live loan, payment or file: taken only from a proved writer who made it, made its loan (making a loan private deletes its payments and files for the family), or is an admin (now or ever seen as one, `family.wasAdmin`). Otherwise kept here and not sent back up (that would only bounce for ever); the screens ask `SyncModel.mayDeleteHere` first and say "Only <name>, who added this, or a family admin can delete it.", so an honest phone never makes such a delete.
6. Dirty here: the newer of the two wins (updatedAt, then updatedBy).
7. Clean here: taken when it is the same version or newer; an older row is refused and this phone's copy is marked dirty, so the newer copy goes back up.

Writes stamp `updatedAt = max(now, min(previous + 1, now + 10 min + 1))` (`SyncModel.stamp`, used by `touch`): an edit made on a phone whose clock is behind still beats the version it edits, and nothing is ever stamped far ahead. A tombstone keeps the previous stamp before it is touched.

### Who wrote what

- **Record signatures.** Every pushed envelope carries `sig: { by, s }` beside `{ k, r }`: an ECDSA P-256 (SHA-256) signature by the pushing member's family key over `"tally-rec|1|<family>|<kind>|<id>|<by>|" + JSON(r)` (`Membership.signRecord`). The receiving phone verifies it against its pin for `by` (`Membership.BookTrust`); unsigned rows (older versions), unknown keys and bad signatures count as unproved. A phone sending someone else's copy unchanged (sending it back up, rule 3 or 7) attaches the signature it arrived with, kept beside the record as the local-only field `sig`. Older readers ignore the extra envelope field.
- **Key certificates.** When an admin lets someone in (or back on a new phone) it writes that member's record with `cert: { by, s }`: its signature over `"tally-pin|1|<family>|<member>|<pub>"` (`Membership.cert`). Other phones pin a member's key from a record only through a certificate by a member they have seen as an admin whose key they have pinned (`pinFromCerts`, repeated until nothing more is learnt), never from `pub` alone. A certificate is for one key: a record whose key changes drops it, and a phone keeping its own newer copy adopts the certificate of a pulled copy with the same key.
- **Older books:** once per book (`sync.signed`), a phone sends its own member record again, signed, so phones that take member records only from a proved writer keep its name. Mixed versions: a phone on 0.5.0 or older sends unsigned rows, so the newer phones ignore its member-record changes and its deletions of entries; update every phone.

Refinements in `sync/`:
- A dirty mark is cleared after a successful push only if the record has not changed since it was collected (an edit during the push stays dirty).
- A record that is private on this phone is never replaced by a pulled row. If someone else's edit of it arrives, it is ignored and the record is marked dirty again, so this phone's tombstone goes back up and wins.
- Pushing a private record: if its id is in `sync.pushed` the push is a bare tombstone `{ id, deleted: true, updatedAt, updatedBy }`, otherwise nothing is sent. A payment or file whose owner cannot be found counts as private when pushing (fail closed).
- Creating a family marks every record dirty and every live file for upload, so the creator's loans are shared. Entering one by approval holds them back until the person answers (see "Joining", step 6). Leaving removes `family` and `sync` and keeps every record.

Making a shared loan private pushes tombstones for the loan, its payments and its files, and keeps the local copies. Making a private loan shared marks them all dirty.

Sync runs when asked (pull to refresh, the Sync button), once each time the book becomes ready (app open or after unlock) if a family exists or a join is waiting, and after every membership action. A sync started from a screen runs in the app's own scope (`Sync.detached`), so closing the screen does not stop it halfway.

A file's bytes are also fetched on open while the relay holds them (`SyncEngine.fetchFile`). A private loan's files stay in `sync.blobsUp` and are never uploaded, nor offered again on an ask; a tombstoned file is dropped from the queue, and one owed but deleted here is acknowledged without being downloaded.

### Notices

No push service and no Firebase. Join requests reach an admin as:
- `SyncEngine.requests` (a `StateFlow<List<JoinRequest>>`), refreshed by every sync, which runs when the app opens or is refreshed: the home card is built from it.
- A quiet background check (`sync/Notices.kt`): a WorkManager periodic job every 4 hours, network required, scheduled only while this phone is an admin. It calls `tally_pending` with the **notice token** (kept in `DevicePrefs` as `tally-notice`, because the worker runs while the book may be sealed; the book keeps its own copy so a restore brings it back on the first sync) and, when more requests wait than the app last saw, posts one notification on the channel "Family": "Someone wants to join your family" / "Open Tally to answer." It names nobody and shows nothing from the book, so it is safe on a locked phone. Tapping it opens the app on the Family page (`MainActivity.EXTRA_OPEN`, taken after unlock). On Android 13+ it needs `POST_NOTIFICATIONS`, asked through `ui/family/rememberNoticePermission()` at a moment the screens choose.

While the app is open (`ui/family/FastJoin.kt`, in the unlocked shell, only while the lifecycle is STARTED): an admin's phone calls `SyncEngine.refreshRequests()` every 5 seconds, and a phone waiting to join calls `checkJoin()`. `refreshRequests()` is the cheap path: one `tally_pending` count with the notice token, and only when that count moved it reads the family's state and re-checks the requests (no pull, no push, no "Syncing" state, never waits for a running sync, silent on failure). `PollPacer` slows to every 30 seconds after 2 minutes with no new request and no touch (`MainActivity.dispatchTouchEvent` calls `FastPoll.touch()`), and speeds up again on either; one call at a time. The background job above is unchanged.

### Payment reminders

`data/DueNotices.kt`: a daily WorkManager job around 9:00 device time posts at most one quiet notification, on its own channel ("Payment reminders", low importance): "Payments are overdue", "A payment is due today" (money I took) or "Money is expected today" (money I gave), with "Open Tally to see." It names no person, entry or amount, so it is the same on a locked phone and while amounts are hidden; tapping it opens the home screen. It is never posted while the app is on screen. Because the job runs while the book may be sealed by the app lock, it reads only a device copy of the **dates** on which something is due or expected (`DevicePrefs` `tally-due-cache`: from `dueDatesAhead(today, 60)` in `model/Reminders.kt`, which walks each open loan's own schedule; dates plus a taken/given flag, no names, ids or amounts; never in a backup; everything already overdue is kept as its single oldest date per direction, so the cache is at most about 60 dates each way), kept in step with the book a moment after each change (`DueCacheKeeper` in the shell). So it covers every due date in the 60 days after the last refresh; a date that has passed counts as overdue until the next refresh after it was paid (opening the app, or any change to the book). The widget (see Widget) shares this copy. The setting "Payment reminders" (Family page, on unless switched off; `tally-due-notices`) is the only switch; on Android 13+ nothing shows until notifications are allowed, asked with the same plain question as the join notice, once, right after the first loan is saved, or when the switch is turned on.

- **Look:** a rounded card in the app's label colours with system red for overdue. Glance cannot read the app theme, so light and dark follow the **phone**, not the in-app Appearance setting.

### Files

- Stored locally as in Balance (`data/Files.kt`: byte-for-byte, SHA-256 checked). **Each phone keeps its own copy** of every file it added or downloaded, and backups include them.
- Photos taken or picked for a payment are scaled to at most 1600 px and saved as JPEG before they are stored, so the stored bytes are what syncs.
- Documents keep their original bytes. Limit: 4 MB per file.

**Files pass through the relay only in transit** (`supabase/migrations/20261112111559_tally_files_in_transit.sql`, `SyncEngine` step 5, mirrored by `FakeRelay`; tests `SyncFilesTest`). The relay's free tier has a 500 MB database, so it no longer keeps file bytes; the file **record** (name, size, SHA-256, owner, who added it) still syncs as an ordinary record for ever, so every phone knows every shared file exists.

- **Upload.** A phone uploads each new shared file once (sealed as before). The relay stores it for 30 days and records who is **owed** it: every member active at that moment except the uploader (`tally_blob_owed`, by member id). A file nobody is owed (a family of one) is not kept at all.
- **Download and acknowledgement.** Every sync asks `tally_files` for the files this member is owed and downloads all of them (they are small: photos are scaled; on Wi-Fi or mobile alike, within the family's limits). A file is acknowledged (`tally_blob_ack`) only after its bytes opened under the family key, matched the record's SHA-256, were stored, and read back matching again; a download that does not open, does not match or is not stored intact is not acknowledged (it is tried again next sync). A file this phone already holds, or has deleted, is acknowledged without downloading. Opening a file also fetches it while the relay holds it, and acknowledges it the same way.
- **Deletion.** When nobody is owed a file any more, the relay deletes it in the same call. Anything not fully collected is deleted after 30 days regardless (swept by the family's next file call and by the daily `tally_ping`).
- **Who is owed what.** Members who join later are **not** owed older files. A member who is removed or leaves is owed nothing any more (a trigger on `tally_member` drops their rows and their asks), so a file is not held for them. **A member back on a new phone** (`tally_member_reclaim`) keeps the same member id and stays active, so **they keep owing**: the new phone fetches what the old one had not collected (the owner's choice: the person, not the phone, is owed the file; a restored backup already has the bytes and simply acknowledges them).
- **On someone's phone.** A phone that lacks a file's bytes (joined later, away more than 30 days, restored without files, or the file is simply not collected yet) shows it, with its name and the date it was added, as **"On <name>'s phone"** (the member who added it), or **"On your other phone"** when that member is this one; never as an error. A tap tries the relay first ("Getting the file…"); if the relay no longer holds it, it explains: "This file is kept on <name>'s phone and in their backups. Tally's server holds a file only until everyone in the family has it." and offers **Ask for this file** (only for a shared file while in a family; `ui/loans/FileAway.kt`).
- **Ask for this file** (`SyncEngine.askForFile`, `tally_file_ask`). If the relay still holds the bytes, the asker is added to those owed and fetches them at once. Otherwise the ask is kept for 30 days and every other active member's sync sees it in `tally_files.asks`; **any** phone that holds the bytes (checked against the record) and for which the file is not private uploads them again, owed then to the askers only, for 30 days. The ask carries only the file id (already the record's id on the relay) and is authenticated with the member's credential like every call; there is nothing in it to seal. One asker's phone collecting the file acknowledges and closes its ask.
- **Private** loans' files never leave the phone (unchanged): never uploaded, never offered on an ask.
- **Limits:** at most 50 MiB of files in transit per family (`TA003` beyond it: the phone keeps the rest queued and tries again on a later sync), a sealed file at most 6 MiB, 500 open asks per family.
- **On screen:** when files are added to a shared entry (a shared loan's Documents, or a payment's attachments while in a family) one quiet line sits under them: "Your family gets a copy. Each phone keeps its own; Tally's server holds it only until everyone has it." The words wrap (Easy mode, large text).
- **The migration** cleared `tally_blob` (sealed test files without timestamps, so their age could not be told; there were none on 2026-11-12) and reset `blob_bytes`.

## App lock

`data/Crypto.kt` (the seal), `data/LockRules.kt` (pure rules: kinds, recovery code, the phone's sealed copy), `ui/lock/` (`LockScreen` + `LockFlow`, `Bio`, `PhoneLock`, `LockModes`). On screen: the App lock group on the Family page.

**Two kinds, one seal (version 2, from 0.6).** Whatever the kind, the book on disk is one envelope `{ enc: 2, s, i, d, t, l, r, p? }` (`data/Crypto.kt`): the book is AES-256-GCM under a **random 256-bit data key**, and only wrapped copies of that key are stored with it:

- `r` `{ s, i, d }`: the data key under PBKDF2-HMAC-SHA256 (150 000 rounds) of the **recovery code** (20 random digits, `RecoveryCode`, about 66 bits). It opens the book, and every backup made under the lock, on any phone. Both kinds have one.
- `p` `{ s, i, d, dv }` (Tally's own lock only): the data key under HKDF-SHA256(this phone's secret, salt = PBKDF2(PIN, `p.s`), info `tally-lock-pin`). **This phone's secret** (`Crypto.device`, `ui/lock/DeviceKey.kt`) is 32 random bytes made once and kept in the app's SharedPreferences `devicekey` sealed under an Android Keystore AES-256-GCM key (`tally-device-key`, no user authentication: the PIN check in the app gates the screen; the Keystore only makes sure the bytes cannot be used off this phone). `dv` names the phone (72 bits derived from the secret, not secret) so a backup from another phone asks for the recovery code at once. If a phone's Keystore cannot make a key at all, the secret is kept unsealed in that private SharedPreferences (never in the book or a backup).
- `s` is the lock's id: `p.s` for Tally's own lock, `r.s` for the phone's lock. A device copy (fingerprint `Bio`, the phone's lock `PhoneLock`) keeps `{ s, k }` with `k` = the PIN's PBKDF2 key or the recovery code's PBKDF2 key, and fits only the lock with that id. `t` is the kind, `l` a PIN's length (it sizes the pad).

The wraps use AES-GCM with the additional data `tally-lock:r` / `tally-lock:p`. The files are sealed under `DB.filesKey`, which lives inside the sealed book, so a lock change rewrites no file. The family's keyring, this member's private key, relay secret and notice token are inside the book, so they are sealed exactly like the loans in both kinds. The recovery code is kept inside the sealed book (`DB.recoveryCode`) so "Show recovery code" can show it again after a check; it is never in a plain book.

**Changing:** a change of PIN (pattern, password) or a switch between the kinds keeps the data key and the recovery code (its wrap `r` stays): only `p` (and the lock id) is new, so the paper the person has keeps working and older backups of this lock still open with it. Turning the lock off forgets both; setting one again makes a new data key and a new code.

**What an attacker needs (the resulting offline cost, one RTX 4090 at about 9×10⁹ PBKDF2 iterations/s):**

| Path | Before 0.6 | Now |
|---|---|---|
| A backup or `ledger.json` copied off the phone, Tally's own lock | the PIN: a 4-digit PIN in under a second, 6 digits in 17 s, any pattern in 7 s | the PIN alone is useless (it needs this phone's 256-bit secret, kept by its Keystore); the recovery code: 10²⁰ × 150 000 iterations, about 5×10⁷ years |
| The same, the phone's lock | the recovery code, out of reach | unchanged: the recovery code, about 5×10⁷ years |
| The phone itself, locked app, guessing through Tally's screen | unlimited, about 1 s per guess | 5 free, then waits of 30 s, 1 min, 5 min, 15 min and 1 hour each, kept across restarts: all 10 000 4-digit PINs take over a year |
| The phone with code running as the app (root, a forensic agent that can call the Keystore) | the PIN off the phone, as above | the PIN on the phone's own CPU through its Keystore (the waits are skipped): about 0.3 to 1 s per guess, so a 4-digit PIN in hours; a long password or the phone's lock is the defence there |
| A backup made before 0.6 that already left the phone | the PIN | still the PIN: a copy already sent cannot be changed. Folder copies are sealed again (see "Backups") |

**Moving to version 2:** a book sealed by 0.5 (`enc: 1`, the book under PBKDF2(secret, `s`) itself) still opens. On the first unlock after the update (`Ledger.open`) it is re-sealed at once under a new random data key: for Tally's own lock the old key becomes the PIN's key with the same `s` (so the fingerprint copy still fits) and a **new recovery code** is made, put in the book and shown once after the unlock ("Tally now has a recovery code", typed back; asked again at each unlock until it is, `Ledger.NEW_CODE`); for the phone's lock the old key becomes the recovery code's key with the same `s` (so the phone's Keystore copy still fits, no prompt needed) and the code stays. A 0.5 backup restores the same way (its PIN or code, then moved to version 2 as it is put in place). The old key is remembered for the session (`Crypto.remember`) so older backups can be sealed again.

- **Tally's own lock** (`t`: `pin`, `pattern` or `password`; `l` the PIN's length): the secret is what the person enters, together with this phone's secret. Setting a first lock asks the PIN twice, then shows the recovery code and has it typed back (cancelling there changes nothing). **Unlock with fingerprint** (`Bio`, optional) keeps a copy of the PIN's key `{ s, k }` under an Android Keystore key usable only after a strong biometric; that key *is* invalidated when fingerprints change, which only turns fingerprint unlock off (the PIN still opens the book). **Forgot the PIN:** the lock screen's "Forgot your PIN? Use recovery code" opens the book with the code and then offers a new PIN (`LockFlow.pickNew`, no old PIN asked; the data key and the code stay). A book whose PIN cannot work on this phone (restored from another phone, or this phone's secret is gone) goes straight to the code and then requires a new PIN for this phone.
- **The phone's lock** (`t: "phone"`, `l: 0`; offered only on Android 11+ with a secure screen lock, `KeyguardManager.isDeviceSecure`): there is no PIN; the recovery code's key `{ s, k }` is also kept on this phone sealed under an Android Keystore AES-256-GCM key (`tally-phone-lock`) made with `setUserAuthenticationParameters(0, AUTH_BIOMETRIC_STRONG or AUTH_DEVICE_CREDENTIAL)` (one use per prompt) and `setInvalidatedByBiometricEnrollment(false)`. The sealed copy is in the app's own SharedPreferences `phonelock` (device-only, never in the book or a backup) and names its lock id, so a copy never opens a book sealed by another lock. Every day the system prompt (`BiometricPrompt`, `BIOMETRIC_STRONG or DEVICE_CREDENTIAL`, with the Keystore cipher as its `CryptoObject`) opens that copy, which unwraps `r` (`Ledger.unlockWithKey`); the recovery code opens the book directly. Choosing it from Tally's own lock keeps the same code (no new paper); from Off it makes one, shown once and typed back.
- **Why a recovery code and not the Keystore key alone:** a Keystore key is destroyed when the screen lock is removed, never exists on another phone and can never go into a backup. A book sealed only by it could be lost for good. With the code the person can always get back in, and a backup is useful on a new phone. One code for the life of the lock (a change of PIN or kind keeps it; turning the lock off and on makes a new one), so every backup made under it opens with the same paper.
- **Android 10 (API 29):** a Keystore key cannot be bound to "screen lock or strong biometric, per use" there, and BiometricPrompt cannot combine a crypto object with the screen lock before Android 11. The phone's lock is therefore not offered on Android 10 (the row says "Needs Android 11 or newer"). A phone-lock book that reaches an Android 10 phone (a restore) opens with its recovery code each time, and the person can switch to Tally's own lock.

**Switching, changing and turning off** all confirm the current lock first (`LockFlow.confirm`: the fingerprint, then the PIN, pattern or password; for the phone's lock the phone's prompt, or the recovery code when the phone's copy is gone). The new lock is made complete before anything depends on it: choosing the phone's lock explains, confirms, shows the code, has it typed back, and runs one phone prompt to seal the copy; only then does the key change in memory and the book get written under it (any step that stops changes nothing). Leaving the phone's lock writes the book under the new secret first and only then forgets the Keystore copy, so a crash in between leaves a book the recovery code still opens. A lock change also turns fingerprint unlock off (`Bio.disable`); `lockChanged()` re-seals the files and clears the widget's snapshot.

**The lock screen** for the phone's lock shows no pad: the system prompt appears by itself, once per lock (a cancelled prompt waits for **Try again**, so the prompt can never call itself up in a loop); "Use recovery code" swaps in a box for the 20 digits (Telugu and Devanagari digits, spaces and dashes are accepted). When this phone holds no fitting copy the box shows at once with the reason.

**Failure cases:**

| What happened | What the person sees |
|---|---|
| Wrong PIN, pattern or password | "Wrong PIN." and the pad again; from the fifth wrong try in a row a wait (below) |
| Forgot the PIN (Tally's own lock) | "Forgot your PIN? Use recovery code", then "Choose a new PIN?" |
| Tally's own lock, a book or backup from another phone | Straight to the recovery code ("This backup was made on another phone…"); afterwards a new PIN is chosen for this phone |
| Prompt cancelled | "Tap Try again to unlock." Nothing changes |
| Too many tries, a sensor error | "That didn't work. Try again, or use your recovery code." |
| Phone's screen lock removed (Android destroys the key) | "Tally can't use this phone's screen lock any more: it was turned off, or this is another phone. Enter your recovery code to open Tally." After the code: if the phone is secure again, "Use the phone's lock again?" (one prompt makes a new copy; the code stays the same), otherwise "Tally will ask for your recovery code each time." Never a crash, never a wipe |
| Fingerprints added or removed | Nothing: the phone's-lock key is not invalidated by enrolment (fingerprint unlock of Tally's own lock turns off, the PIN still works) |
| Screen lock changed to another PIN | Nothing: the key survives a credential change |
| New phone, restore of a phone-lock backup | The restore asks for the recovery code; afterwards the phone's prompt is offered on the new phone |

**Wrong tries** (`Attempts` in `data/LockRules.kt`, `lockGate` in `LockScreen.kt`): every check of a typed secret against a seal (unlock, confirm, the sealed-file stage of a restore, the recovery code) counts. The first 5 wrong tries in a row cost nothing; then each waits 30 s, 1 min, 5 min, 15 min, then 1 hour each. The count and the time of the last wrong try are in `DevicePrefs` (`tally-lock-fails`, `tally-lock-failed-at`; device-only), so closing the app or restarting the phone does not reset them; a clock set back restarts the wait from now. A right answer (or the fingerprint or the phone's prompt) resets it. Nothing is ever wiped. The fingerprint and the phone's prompt are not held back (the system limits them).

**In memory:** the re-lock (`Ledger.relock`) writes the book, drops it from memory, zeroes the data key and any remembered older key (`Crypto.forget`; `Crypto.locked` stays true) and deletes the viewer copy of a document. Strings in the dropped book (the files key, the recovery code) cannot be zeroed in the JVM; they become garbage. The sync engine's in-memory invite checks are the sync code's (`sync/`).

**`holdLock`:** every phone prompt, share sheet, picker, viewer and camera the app opens sets `MainActivity.holdLock` (the time it was set); coming back within the re-lock delay never re-locks, and coming back later re-locks unless the hold was set at most 2 minutes ago (`LockRules.HOLD_MS`, or the re-lock delay if that is longer; `LockRules.relockOnReturn`). So a viewer left open on a phone that was put down no longer keeps Tally open: hours later the lock is asked. A phone prompt also clears the hold 1.5 s after it answers, because the screen-lock page it can show may stop the activity and hand back its answer before `onStart`.

**Screenshots** (`ui/lock/ScreenGuard.kt`, `LockRules.secureWindow`): the window has `FLAG_SECURE` while a lock is set (the lock screen included) or amounts are hidden, so screenshots and screen recordings come out black and the recents card is blank; and always while the invite sheet (its QR is a live invite) or the recovery code sheet is up. Dialogs and sheets inherit it.

**Outside the app:** `Crypto.locked` is true for both kinds, so the widget never keeps a name or amount (`NextPaymentData.snapshotText`) and the reminder and join notices name nothing, exactly as with a PIN.

**Hide amounts:** hiding never asks. Showing them again asks the app lock when one is set (fingerprint first, then the PIN, pattern or password, or the phone's prompt), otherwise the phone's own lock when it has one (`BiometricPrompt` without a key: `BIOMETRIC_STRONG or DEVICE_CREDENTIAL`, on Android 10 `BIOMETRIC_WEAK or DEVICE_CREDENTIAL`), and with neither it simply shows them; the row's subtitle says which ("Showing them again asks for your fingerprint or lock" / "Anyone can show them again: this phone has no screen lock."). Rules in `LockRules.unhideAsk`.

**Threat notes.** The lock protects a phone at rest and a backup file from someone who has the device or the file but not the secret; see the cost table above. With the phone's lock, anyone who can unlock the phone itself can open Tally (that is the choice the person made); the recovery code on paper is as strong as the book's protection, so it must be kept away from the phone. The Keystore copy cannot be read off the phone (it is used inside the Keystore, and only after the phone's own check). A phone-lock backup holds the same envelope as the disk, so it needs the recovery code and nothing on the phone.

## Backups

`data/BackupCore.kt` (plain JVM: make, check, put in place) and `data/Backups.kt` (the folder, WorkManager, the share sheet, the app's locks); on screen `ui/family/BackupFlow.kt`.

### The file

`Tally-YYYY-MM-DD.tally-backup`, a zip whose entries are all stored (not compressed):

- `book.json`: the book exactly as stored on disk: plain JSON, or with a lock the sealed envelope `{ enc, s, i, d, t, l, r, p? }` (see "App lock").
- `files/<id>.bin` and `files/<id>.json`: every stored file and its record exactly as on disk (the original bytes, or with a lock AES-GCM under `DB.filesKey`, which is inside the sealed book). So a backup taken with a lock opens on the phone that made it with its PIN (pattern, password), and on any phone with the recovery code alone (this phone's secret and the Keystore copies never go into a backup). The first time a backup is sent off the phone under a lock, the recovery code is offered once more ("A backup opens on a new phone only with your recovery code. See the code now…", behind the lock; `LockModes.beforeFirstSend`).
- `manifest.json`, written last: `{ format: "tally-backup", version: 1, app, createdAt, date, sealed, counts?, skipped?, entries: [ { name, size, sha256 } ] }`. `counts` (`loans`, `payments`, `files`, tombstones not counted) only for a plain book.

A backup copies what is on disk, so it needs no secret and runs while the app is locked or not running. It is taken under `FileStore.filesExclusive` (no lock pass or downloaded file meanwhile), each record read under `FileStore.io` and the book under the ledger's disk lock, so it never copies a half-written file (AtomicFile on Android 10 rewrites in place behind a `.bak`; a `.bak` left by a crash is read as the good copy). An open book is saved first.

Not in a backup: anything device-only (language, the backup folder and its state, fingerprint unlock, the phone's-lock Keystore copy, the re-lock delay copy in `DevicePrefs`, the notice token copy for the background check, WorkManager's own records). Everything in the book is: loans, payments, private loans, files, `me`, `family` (its keyring, this member's relay secret, notice token and private key), a waiting `joining`, and `sync`.

Without a lock the file is plain and contains the family's keys and this member's credentials: whoever has it can read the family's entries and act as this member until an admin removes them. The Backup group's footer and the share question say so in one line ("anyone who gets this file can read your entries and join your family").

### Daily, and Back up now

- "Back up every day" asks for a folder once (`ACTION_OPEN_DOCUMENT_TREE`, a persisted permission kept in `DevicePrefs`; no storage permission, no account, no network). A WorkManager periodic job runs once a day, and on every app open a one-off job runs if the last backup that worked is more than 24 hours old (battery savers delay workers). At most one a day: a second backup the same day replaces that day's file. The file is written as `….tally-backup.partial` and renamed when complete; then the folder keeps the newest 14 files with Tally's own name and touches nothing else.
- A folder that is gone or no longer allowed sets "stopped": the Backup group and a quiet line on the home screen say "Backup stopped: choose the folder again". Another failure shows "It did not work last time" and tries again next time.
- "Back up now" saves into the folder (when one is chosen), makes the file in the app's cache and, after one question, opens the share sheet (Drive, WhatsApp, email). The cache copy is deleted at the next start and at a lock change.
- A document opened in a viewer is written plain to `cache/shared` (the viewer needs the bytes); that copy is deleted when Tally comes back to the front, when it locks again and at every start (`FileStore.clearViewCopy`). The cache is never in a backup.

### Send a copy off the phone (monthly reminder)

The daily backups sit in a folder on the phone, so a lost phone loses them too. `data/BackupReminder.kt` keeps, in `DevicePrefs` only (`tally-backup-sent`, `tally-backup-snooze`, `tally-first-use`; never in the book or a backup), when a backup last left the phone. The home screen shows a quiet card under the figures ("Send a copy of your backup somewhere safe, like Google Drive or WhatsApp to yourself." with Send now and Not now) when that was more than 30 days ago, or never once the book has a loan and the app has been used for 7 days; Not now hides it for 7 days; Send now runs Back up now. The Backup group has a "Last sent off this phone" line (date or Never) that is also the way in while the reminder is due. The rule is the pure `BackupReminder.due`. No notification: it shows only inside the app. The no-lock warning stays in the share question, not on the card. The card stacks its buttons in Easy mode and at large text.

How "sent" is detected, and its limit: the share sheet is opened with a chooser `IntentSender`; when the person picks an app Android reports it and the copy counts as sent (the app picked is not kept). Some phones' choosers do not report; then, if the app comes back to the front at least 8 seconds after the sheet opened, it counts. Android never confirms that the target finished, so a person who picks an app and then cancels inside it is still counted, and one who closes the sheet quickly (under 8 seconds) is not.

### Restore

From the Family page ("Restore from a backup") or the welcome screen ("I have a backup"):

1. The picked file is copied into the cache (at most 2 GB) and checked completely before anything changes: a zip; only the names above (no folders, paths, traversal, duplicates); manifest format and version 1 (a newer version says "update Tally first"); every entry listed with the right size and SHA-256 and every listed entry present; caps (manifest 8 MB, book 64 MB, a file 16 MB, 20 000 entries); a book that is a Tally book or an envelope, as the manifest says.
2. Sealed: on the phone that made it the PIN (pattern, password) is asked, elsewhere (and always for the phone's lock) the 20-digit recovery code (the lock screen's "sealed file" stage, which counts wrong tries), and checked against the backup's envelope without touching the current lock. A backup from before 0.6 asks for its PIN and is moved to the new seal (a new recovery code, shown after the restore).
3. One question (`Dialogs.ask(…, danger = true)`) with the backup's date, its loans and what is replaced, and the one limit: shared loans and payments the family deleted since stay deleted. A restore is not an undo for the family.
4. With the sync engine paused, the files lane held and saving frozen: the current book and files are written as the one safety copy (`filesDir/restore/before-restore.tally-backup`, replacing the last); the backup is unpacked into staging (hashes checked again); a journal marks it complete; the files folder and the book are swapped in. A failure before the swap changes nothing; a process that dies during the swap finishes it at the next start (`Backups.init`, before anything is read). The book is started fresh (`Ledger.start`) with the lock set as below, still inside the lane.
5. "Undo the last restore" puts the safety copy back the same way (its PIN if it was locked) and then deletes it.

The lock after a restore:

| Backup | Phone before | After |
|---|---|---|
| locked, this phone | no lock | locked with the backup's PIN |
| locked, another phone | any | opened with the recovery code; locked with that lock and its code, and a new PIN is chosen for this phone right after |
| phone's lock | any | asks the backup's recovery code (or, for a backup of this very lock on this phone, such as an undo, the phone's prompt); locked with that lock, then "Use the phone's lock again?" sets up this phone's prompt when it can, else the code is asked each time |
| locked | locked | locked with the backup's PIN (fingerprint unlock is turned off; the app says so) |
| plain | no lock | no lock |
| plain | locked | stays locked with the phone's own PIN (or the phone's lock, with its recovery code carried into the restored book): the book is sealed with it as it is written, and the lock pass seals the files. Restoring must never silently remove a lock the person set. |
| undo | any | as before the restore (locked with that PIN, or unlocked), except that a safety copy sealed again after a lock change (below) opens with the lock of that time |

### After a lock change: older copies sealed again

When a lock is set or changed, or a 0.5 book is moved to the new seal (`data/BackupReseal.kt`, `LockModes.afterLockChange`):

- the restore safety copy (`filesDir/restore/before-restore.tally-backup`) is sealed again under the current lock, silently;
- the share-sheet copy in `cache/backup` is deleted;
- Tally's own backups in the daily folder that are plain, or sealed by an earlier lock of this book that this session still knows (the 0.5 key from the upgrade, an earlier data key), are found, and the person is asked once per lock: "Older backups in your folder are not locked. Lock them now?" (or "…still use your old lock. Lock them with the new one now?"). Yes rewrites each one (`BackupCore.reseal`: the book sealed under the current lock with its kind and recovery code, plain files sealed under the book's files key, made if needed; already-sealed files kept byte for byte; the same date, name and createdAt), checked before it replaces the old file. No is remembered for that lock; those files leave the folder within 14 days.

A backup sealed by a lock this phone does not know is left alone. Daily backups after the change copy the sealed book, so they are sealed. Copies that already left the phone (Drive, WhatsApp) cannot be reached: a 0.5 backup sent off the phone stays as strong as its old PIN.

### Restore and sync

The restored book keeps its `sync` (cursor, dirty marks, `pushed`, `blobsUp`), so the next sync pulls everything the family wrote since the backup's cursor and the normal rules apply: records the phone had not changed take the family's copy; edits still dirty in the backup meet the family's by last writer; deletions stay; a file whose bytes are not here is fetched as usual.

One case needs more: a loan that was private in the backup but shared since (by this phone, before the restore). The normal rule would answer the family's newer copy with a tombstone and delete the loan on every phone. So a restore sets `sync.restored`, and until the next complete sync a pulled row that is newer than a private copy here (loan, payment or file) is taken. Covered by `SyncRestoreTest`. Limits: a loan made private after the backup comes back as the family's tombstone (it was deleted for them); the same backup restored on two phones at once makes them one member (one set of credentials, one key pair).

Membership after a restore: see also "Back on a new phone" (the recommended order, and `keepNewerSeat`). The restored phone is the same member (same member id, relay secret and key pair), so it keeps working; keys made after the backup are in its boxes on the relay and open on the first sync (`SyncMembershipTest.aRestoredPhoneIsStillTheSameMember`). If the member was removed since, the first sync says so and forgets the family. A backup taken while a join request was waiting restores that request.
